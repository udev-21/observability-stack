================================================================================
 NGINX json_analytics (EXTENDED) — FULL METRICS CATALOG
================================================================================

CONTEXT
-------
Catalog of every metric derivable from the EXTENDED nginx json_analytics log
(original fields + the additions: tcpinfo_rtt, http2, request_completion,
sent_http_content_type, upstream_status, upstream_queue_time,
upstream_bytes_received, upstream_bytes_sent, ssl_session_reused,
ssl_server_name, limit_req_status, limit_conn_status).

Pipeline reality (Shape A): nginx access.log -> Vector -> { VictoriaLogs (raw
logs) + VictoriaMetrics (derived metrics) } -> Grafana. So each row is realizable
two ways: as a Vector log_to_metric series (bounded fields only) OR as an
on-demand LogsQL/PromQL query.

KINDS
  Counter      monotonic count (-> rate/sec)
  Distribution numeric spread -> histogram buckets (avg, p50/p90/p95/p99, max)
  Ratio        QUERY-TIME division of two counters (NOT a stored series)
  Unique       distinct-value cardinality -> LOGS ONLY (LogsQL uniq/count_uniq;
               a stateless log_to_metric cannot produce true distinct-over-time)
  Derived      QUERY-TIME expression over other metrics (NOT a stored series)

(!)   = high label cardinality -> normalize / top-N / keep in logs, never a raw label.
(NEW) = unlocked by a field added in the extended log_format.

================================================================================
 CARDINALITY GUIDANCE (read before turning any row into a stored series)
================================================================================
1. BOUNDED label whitelist (safe to put on a metric):
     status, status_class, request_method, scheme, server_protocol, http2,
     http_host/server_name, ssl_protocol, ssl_session_reused, ssl_server_name,
     upstream, upstream_cache_status, upstream_status, geoip_country_code,
     limit_req_status, limit_conn_status, normalized content-type, normalized route.

2. (!) fields (request_uri, remote_addr, http_user_agent, http_referer,
   ssl_cipher, raw content-type, forwarded IPs) -> NORMALIZE or keep in logs.

3. Histograms cost (buckets + 2) series PER label combination. Your latency
   histogram (status_class x method x host x route x ~13 buckets) is already the
   single biggest series driver. Every extra Distribution row multiplies again.
   Prefer FEW labels on histograms; consider dropping `route` from histograms.

4. tag_cardinality_limit caps each tag INDEPENDENTLY (value_limit per key) - it
   does NOT bound the COMBINATORIAL PRODUCT status x method x host x route x ...
   The product is the real OOM risk; keep the number of labels small.

5. Ratio / Derived rows are PromQL at query time, not new series. Unique rows are
   LogsQL over VictoriaLogs, not metrics. Don't try to "emit" them.
