================================================================================
 NGINX json_analytics — FULL METRICS CATALOG
================================================================================

CONTEXT
-------
The stack ships nginx JSON access logs (json_analytics log_format) into
VictoriaLogs via vlagent. Before building dashboards/alerts (or a Prometheus-
style exporter), this is the complete set of metrics derivable from the log
fields — "squeeze everything" — so we can pick what to implement and know what
each field is worth.

Syntax-free: each row = a metric concept, its source field(s), its kind, the
dimensions it can be sliced by, and notes. Applies equally to a metrics-exporter
pipeline (counters/histograms) or to LogsQL stats over VictoriaLogs.

KINDS
  Counter      monotonic count (-> rate/sec)
  Distribution numeric spread (avg, p50/p90/p95/p99, max)
  Ratio        percentage of two counts
  Unique       distinct-value cardinality
  Derived      computed from other metrics

(!) = high label cardinality — do NOT label a time-series metric by this raw;
      normalize, use top-N, or keep it in logs instead.

--------------------------------------------------------------------------------
K. NON-METRIC FIELDS
--------------------------------------------------------------------------------
request_id                    -> not a metric; correlation key to jump from a
                                 metric anomaly to the exact log line (keep for drill-down).
time_local/time_iso8601/msec  -> the timestamp; enables seasonality views
                                 (by hour/weekday) but isn't itself a metric.
remote_port                   -> ephemeral client port; negligible value, skip.


================================================================================
 CARDINALITY GUIDANCE (the one rule that matters)
================================================================================
For pre-aggregated metrics (a /metrics exporter or recording rules), only use
BOUNDED fields as labels: status, request_method, scheme, server_protocol,
http_host/server_name, upstream, upstream_cache_status, ssl_protocol,
geoip_country_code.

Everything marked (!) (request_uri, remote_addr, http_user_agent, http_referer,
ssl_cipher, forwarded IPs) must be either NORMALIZED (collapse path IDs, group
UA into bot/browser families) or left to on-demand log queries / top-N rather
than a labeled time series — otherwise series count explodes and the TSDB OOMs.

================================================================================
 IMPLEMENTATION MAPPING (no code yet)
================================================================================
- Possible today: every row works as a LogsQL stat over the logs in
  VictoriaLogs (on-demand aggregation). The existing nginx-analytics.json
  dashboard already covers ~10 of these.
- For cheap dashboards/alerts at scale: the bounded (non-!) rows become
  exporter counters/histograms scraped into VictoriaMetrics
  (prometheus-nginxlog-exporter -> vmagent -> VictoriaMetrics). (!) rows stay
  in logs.
